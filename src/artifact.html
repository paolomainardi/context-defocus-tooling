Context defocus tooling.
A working reference.

A reference catalogue of open-source tools that address token consumption and context degradation in AI coding agents (Claude Code, GitHub Copilot, OpenCode). Organized by the failure mode each tool targets. Filter and sort by community metrics. Vendor claims are presented as such; independent measurements are cited when they exist.

Context defocus. A 1M-token window with low-signal noise produces worse answers than 100K with focused information. The cost question (Copilot's usage-based billing transition on June 1, 2026) and the quality question are the same question. Each tool below targets one specific way agents lose signal: noisy command output, raw tool dumps, repeated codebase exploration, broad file reads, model verbosity, or memory loss across sessions.

01 / FAILURE MODES

Five ways agents lose the thread.

Adapted from the Milvus context-management taxonomy (May 2026). Each failure mode is a recognizable pattern. Tools may target one or more. Click any tool tag below to filter the catalogue.
01
Noisy terminal logs
git, pytest, gh, cloud CLIs and build tools dump environment info and verbose status that the model doesn't need. Multiplied across many commands per session.
Tools addressing this rtk lean-ctx (shell)
02
Tool outputs flood the window
Playwright snapshots, gh issue lists, large MCP tool results, scraped pages, build logs enter the chat as giant raw blocks. The signal gets buried.
Tools addressing this Context Mode Headroom token-optimizer-mcp
03
Repeated codebase navigation
The model lists directories, greps, reads files, then repeats the same exploration in the next session. No persistent map of structure or semantics. Expensive in large repos.
Tools addressing this Serena CodeGraph code-review-graph tokensave Claude Context Semble Context+ GitNexus MCP Language Server lean-ctx (MCP)
04
File reads too broad, answers too verbose
Model reads a whole file when one symbol would do; model's own answers are long enough to bloat future turns. Output policy is part of context policy.
Tools addressing this Token Savior Caveman claude-token-optimizer claude-token-efficient
05
Memory gaps across sessions
Project decisions, debugging history, user preferences don't persist. Every new session re-explains the same context. Cross-agent or cross-model handoffs lose all prior state.

03 / OPEN QUESTIONS

What this catalogue cannot answer for you.

Decisions any team adopting tools from this list still needs to make. Listed as questions, not as recommendations.

Decisions left to the reader

  1. Which failure mode hurts your team the most? Without measurement, rollout order is guesswork. A passive telemetry tool in shadow mode for one week produces the data to decide.
  2. Is transparent-proxy integration acceptable? Tools like Headroom intercept the agent → LLM API path. Whether this fits your security model is an organizational call, not a technical one.
  3. What is your bus-factor threshold? Thirteen of eighteen tools here are solo-maintained. Consistent thresholds (minimum stars, contributors, age, fork-and-mirror policy) help narrow categories with many candidates.
  4. How do you handle vendor-affiliated open source? Some tools are maintained by commercial entities with adjacent paid products. Implications vary by case.
  5. What is your NDA / client-code posture? Tools that phone home, route data through third-party services, or store project memory externally need an explicit policy decision relative to client contracts.
  6. What is the relationship between tooling and org-level cost levers? Token-tooling is one cost lever. Model-selection policy, credit budgets, and prompt-caching discipline are independent levers operating in parallel.
  7. How will you measure savings on your actual workloads? Most vendor benchmarks do not reproduce on production traffic. Independent reproduction is the natural next step before any meaningful rollout.
  8. How will you resolve overlap within a failure mode? Several modes have multiple candidates using different mechanisms (LSP symbols, static call graphs, vector search, progressive reading). Choice rule among them is the largest open design decision.

Methodology and definitions

Star count
Captured early-to-mid May 2026 from project pages and third-party crawlers. Directional, not precise. Daily delta is meaningful in this category.
Maintainer count
Reflects recent commit-graph concentration, not the full GitHub contributors page. Drive-by typo PRs are not counted as multi-maintainer.
Maintainer classification
Team: multiple substantive contributors visible in recent activity. Vendor: project maintained by a commercial entity with adjacent paid products. Solo: single primary author in the recent commit graph.
Independent eval
Requires measurement of reduction or quality by someone unaffiliated with the project's vendor. Vendor-self-reported benchmarks (even reproducible ones) do not count.
Vendor claims
Presented as such (e.g., "vendor reports 65%"). Where independent reproduction exists with materially different numbers, both are cited.
Risk dot
Computed mechanically from four signals: stars (proxy for community adoption), maintainer count (bus factor), independent eval presence (claim verifiability), and release recency (maintenance signal). Thresholds below. Not an opinion; argue with the thresholds, not the dot.

Risk dot thresholds

low
≥10k stars OR team/vendor maintained; AND has independent eval; AND released in the last 6 months.
mid
1k–10k stars; OR solo-maintained with eval; OR vendor-maintained without recent release. Recent-enough activity to suggest the project is alive.
high
<1k stars; AND solo-maintained; AND no independent eval. Project may be early or niche; signal-to-judgment ratio is low.
crit
<50 stars; AND solo; AND no eval; AND no release in 6+ months. Effectively a hobby project with limited validation. Use with explicit awareness.
